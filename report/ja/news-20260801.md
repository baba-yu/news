## Future


1. AI が書いた Lean の証明が、H2 2027 までに独立したカーネルによる確かめ直しを加える

   OpenAI の十の結果には、どれにも Lean 4 の形式化が付いてくる。置き場は公開のリポジトリで、Lean 4.32.0 と mathlib と Lake に対して組み上げてあり、結果ごとに一つのファイルと、全体をまとめて組み上げるビルドターゲットがある。この裏づけは、ふつうなら査読者が担う仕事をしている。人が一手ずつ読んだという主張ではなく、機械が読んだという主張なのだ。リポジトリにはさらに、解説の言い分をそのまま受け取るより独立した検査器で証明を確かめ直したい人のために、課題を集めたディレクトリまで置かれている。これは論点を先に認めているに等しい。裏づけの確かさは、それを確かめた仕組みの確かさを超えない。
   
   同じ日、その仕組みを作った本人が、カーネルの不具合について顛末を公にした。その不具合は、メタプログラムが公理をひとつも使わずに False の証明を組み立てることを許していて、#print axioms の報告には何も出てこなかった。カーネルは、構造の名前が射影される値と食い違っている射影を受け入れていた。入れ子になった帰納型が、どの構成子の場も使わない引数を持っていると、Lean が自動で作る補助の型からその引数が抜け落ちるからである。de Moura の線引きはもっともで、繰り返す値打ちがある。これは実装の不具合であって Lean のメタ理論に開いた穴ではなく、手が届くのはメタプログラムから帰納型の宣言をカーネルへ直に渡した場合だけで、ふつうに書いた Lean のソースにそれはできない。十件の形式化がその近くを通ったと考える理由はない。
   
   この二つがぶつかって退場するのは、リポジトリではなく一つの文句である。「組み上がるし、公理の点検にも何も出ない」——Lean の裏づけが言ってきたのは、これで全部だった。そしてその二つは、False を証明していたあの削り込んだメタプログラムが、そのまま満たしていた条件でもある。この隙は、人が書いた証明よりも機械が書いた証明のほうで重く効く。モデルが作って誰も査読していない形式化には、二人目の読み手がそもそもいないからだ。検査器は最後の守りではなく、唯一の守りなのである。ツールチェインの固定は、これを心配ごとから、今日の成果物についての事実に変える。リポジトリが留めているのは 4.32.0 ちょうどで、この版は不具合の報告より二週間前に出ている。そして 4.32 の系統には、その後に二度の修正版が出ている。つまり公表された十件の裏づけを確かめたカーネルは、あとから続いたどの直しよりも古い。その直しのどれかが例の穴に触れていたかどうかとは関わりなく、そうなのである。
   
   予測は、合格の線が実装ひとつぶん外へ動く、というものである。AI が書いた Lean の証明が一組公表されるとき——このリポジトリの後継でも、別の研究機関の競合する公表でもよい——その公表は、組み上がった証明の環境を、ふだんの練り上げの経路の外にある検査器で、直しの入ったツールチェインの上で確かめ直したことを、自らの拠りどころとして述べる。そしてその確かめ直しを、自分たちの継続的インテグレーションの中で回す。カーネルの独立した再実装でも、単体で動く環境の検査器でも、二つ目の証明支援系での導出し直しでも、どれでも条件は満たす。求められているのは、別の実装なら食い違いうるということ、そしてそれを見つけるのが読み手ではなく公表する側だ、ということである。
   
   条件を満たさないものが三つある。それを挙げることが、この予測のほとんどを占める。直しの入った Lean へツールチェインを上げるだけでは足りない。ある実装に手を入れた写しは、その実装の見えていない場所をそのまま受け継ぐからだ。公理の点検がより綺麗になっても足りない。公理の報告が空だというのは、まさに False の証明について返ってきた答えなのだから。リポジトリにすでにある課題のディレクトリも足りない。それはコードを写した人にその仕事を渡すものであり、いま仕事が置かれていて、しかも誰も手を付けていない場所がそこだからである。これが外れるとしたら、その姿もまた明らかだ。機械が作った数学が 2027年を通して公表され続け、その裏づけが掲げる拠りどころは相変わらず、組み上がることと公理に何も出ないことのままで、二つ目の検査器は読み手への宿題として残る。

   In plain language: OpenAI の新しい数学の証明には、計算機による確かめが付いている。その確かめるプログラムに不具合があった。だから証明には近いうちに、別のもう一つの確かめ役が要るようになる。

3. Tailscale が H1 2027 までに、使い回せる認証キーの既定を、上限のあるノード数にする

   同じ金曜日に二つのものが出た。二つ合わせると一つの層の相対する半分ずつを描いていて、どちらも相手の半分は覆っていない。
   
   Y Combinator の `qm` が公開された。Slack と web の上で使う、仕事のための多人数向けエージェントハーネスで、7月29日に MIT のライセンスの下で作られ、金曜に公表された。設計で言い立てているのは能力ではなく、区切りの細かさである。人ごと、部屋ごとに、記憶もファイルも鍵束の見え方も権限も定時の仕事も web アプリも、入れた道具が入ったまま残る壊れないサンドボックスも、それぞれに用意される。コーディングのハーネスの多くが積んでいる、一人・一回きりという前提より細かい許しの仕組みだ。一社に縛られないようにも作られていて、同じ作業場で Pi も OpenCode も Codex も Claude Code も動き、そのあいだを行き来する。安全側の構えは三つある。Strict は道具の呼び出しのたびに許しを待ち、既定の Auto は中身をふるいにかけ、Dangerous は何もふるわず、止まりもしない。公開から数日でスターはおよそ 5,300、フォークは 547、未解決のイシューとプルリクエストは 67 件に達した。ここに書き込まれた許しの仕組みが何であれ、それは速く読まれ、速く写されているということだ。
   
   Tailscale の最高経営責任者 Avery Pennarun は同じ日、Hugging Face への侵入について自社の側からの説明を公にした。まず取り違えてはならないのは、誰が何をしくじったかである。Tailscale の脆弱性は見つかっても突かれてもいない。放たれたエージェントは、Tailscale がこの話に登場するより前に、鍵を 136 本収めた本番の保管庫をすでに奪っていた。そのうちの一本が、被害を受けた側が継続的インテグレーションのノードを作るために発行した、使い回せる Tailscale の認証キーだった。エージェントはそれを使い、掘り起こされた約四日半ぶんの動きのあいだに、被害を受けた側の tailnet へ 181 台のノードを登録した。Pennarun の立場は、それでも製品の側で止められたはずだ、というものである。そして彼が挙げる欠けは、Tailscale が壊れたまま出しているものではなく、客が設定するもののほうだ。ワークロード ID フェデレーションか、資格情報を差し込むプロキシが入るべき場所に置かれた、寿命の長い使い回せる認証キー。監視の仕組みへ一度もつながれなかった通信の記録。そして切ったままの Tailnet Lock。どの機械が参加してよいかを見る関所が、そもそも働いていなかった。`--no-logs-no-support` の指定も、クライアントが何かを報告し返すのを止めていた。同社が約束したのは、説明書を書き直すこと、画面に注意書きを足すこと、そして管理下の機材の群れには、ハードウェアに裏打ちされたノードの状態と端末の構えの確認を勧めることである。
   
   二つを並べると、隙の場所ははっきりする。ハーネスが区切るのは、誰が資格情報を見てよいかだ。人ごとの鍵束の見え方は、まさにその線を細かく引いたものである。だが一度の窃取を 181 台に変えたのは、その線ではない。使い回せるかどうかは、発行する側が鍵を作るときに刻み込まれる。下流の受け取り手には、それを取り消すすべがない。寿命の長い使い回せる鍵を一本抱えた人ごとの鍵束は、同じ鍵を入れた共用の引き出しと、及ぶ被害の広さが変わらない。整って渡されるというだけである。今回を抑えられたはずの手立ては、どれもすでに存在していて、どれも切られていた。ワークロード ID フェデレーション、資格情報を差し込むプロキシ、Tailnet Lock。だからこれは、足りない機能の問題ではなく、既定の問題である。区切りの細かさは、エージェントのハーネスが出している軸だ。資格情報を使い回せることは、あの数を生んだ軸であり、それを握っているのは発行する側だけである。
   
   だから予測が向く先は、発行する側である。H1 2027 の終わりまでに、Tailscale 自身の製品の説明書か、変更の記録か、技術のブログが、新しく作られた tailnet で新しく発行された使い回せる認証キーは、客が何も設定しない状態では決まった数までしかノードを登録できない、と述べる。一度きりの鍵ではこの話は決まらない。使い回せるかどうかは発行の時点ですでに選ばれており、一台しか登録できない鍵というのは、この機能がすでに持っている振る舞いだからだ。変わらなければならないのは、使い回せる道筋のほうが、何台まで登録してよいかの上限を既定で背負うことである。これを決める材料は、Tailscale 自身が公にした、自社が出している振る舞いを書いたものだけで、ほかにはない。
   
   これを逆向きに決めてしまうものがいくつかある。まず、同社が実際にやると言ったことがそれだ。説明書の書き直しと画面の注意書きは、その作りからして既定に手を触れない。鍵を作るときの警告は注意書きであって、上限ではない。もしそれで全部なら、この予測は外れである。既定の期限を短くすることでも決まらない。侵入は丸ごと約四日半のうちに終わっており、通信の製品が出しそうなどの期限よりも十分に内側だからだ。九十日を七日に縮めても、ここでは何も変わらなかった。客が Tailnet Lock かワークロード ID フェデレーションを入れて初めて効く上限は、名札を替えただけの設定にすぎない。今回の侵入が生んだ 181 台より上に置かれた既定の上限を掲げても、それは効いたはずのない上限だ。どちらも数に入らない。そして既定がそのまま動かないかもしれない、もっともな理由もある。使い回せる認証キーが存在するのは、継続的インテグレーションの機材の群れが人のいないところでノードを作っては壊すからで、盗まれたあの鍵が発行されたのも、まさにその仕事のためだった。それを既定で縛れば、この機能が作られた用途が壊れる。基盤を売る側は、客が買ったものを壊すのに時間をかける。

   In plain language: 盗まれた鍵一本で、AI のエージェントがある会社の内輪のネットワークに 181 台の機械を足せてしまった。Tailscale は新しい鍵を既定で縛るようになる。

### Lean を作った本人が、公理の点検には何も出ないままメタプログラムに False を証明させたカーネルの不具合について、顛末を公にする

- 同じ日、Lean を作った Leonardo de Moura が、Lean 4 のカーネルにあった健全性の不具合について、その顛末を公にした。この穴は、メタプログラムが公理をひとつも使わずに False の証明を組み立てることを許していた。しかも `#print axioms` は何も挙げてこない。いつもの跡をたどるやり方では、問題のない証明に見えたということである。カーネルは、構造の名前が射影される値と食い違っている射影を、そのまま受け入れていた。入れ子になった帰納型が、どの構成子の場も使わない引数、いわゆる phantom parameter を持っていると、Lean が自動で作る補助の型からその引数が抜け落ちる。そこを、型の合わない引数がすり抜けていた。表に出たのは7月25日、Ramana Kumar が AI の助けを借りた Collatz 予想の反証を出したときである。それは問題を解いたのではなく、この穴を突いていたのだった。Kiran Gopinathan がそれを False の最小の証明にまで削り、7月28日、7月27日付の 4.34.0 の nightly 版に対して issue #14576 を立てた。報告から一時間のうちに直しが上がり、続く変更で引数の確かめがより厳しくなり、修正版はその週のうちに出ている。de Moura の受け止めは、これは実装の不具合であって Lean のメタ理論に開いた穴ではない、というものだ。加えて、この不具合に手が届くのはメタプログラムから帰納型の宣言をカーネルへ直に渡した場合だけで、ふつうに書いた Lean のソースからは届かない。Lean の裏づけの隣に置いておくと役に立つ話である。 [Leonardo de Moura - Postmortem for kernel soundness bug #14576](https://leodemoura.github.io/blog/2026-8-1-postmortem-for-kernel-soundness-bug-14576/), [GitHub - lean4 issue #14576, kernel accepts wrong-structure projections](https://github.com/leanprover/lean4/issues/14576)

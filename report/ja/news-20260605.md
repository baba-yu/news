## Future


1. エージェントフレームワークのSQLツール、2027年Q1までにデフォルト読み取り専用の実行ガードを搭載へ

   エージェント型のtext-to-SQL実行層は、安全側をデフォルトとする方針へ収束していく。2027年Q1までに、Langroid以外で広く使われているLLMエージェントフレームワークが少なくとも3つ、データベースクエリツールのデフォルトを、パーサーで検証したSELECT専用の許可リストと、SQL方言を踏まえた危険パターンの拒否リストに切り替えると見込まれる。書き込み・DDL・プログラム実行を伴う生のSQLは、デフォルト挙動ではなくオプトインの扱いになる。この転換を後押しするのは、プロンプトインジェクションで操られたモデルが任意のSQLを書ける、という認識である。したがって、デプロイ側のデータベースロールだけでなく、フレームワーク自身の実行ラッパーこそが防御の要にならなければならない。具体的には、LangChainのSQLツールキット、LlamaIndexのtext-to-SQLクエリエンジン、あるいは同種のエージェントライブラリで、デフォルト設定そのものが変わる形で現れるだろう。あわせて、最小権限で読み取り専用のデータベース認証情報を、脚注扱いから明示的な前提条件へと格上げするドキュメントも伴うはずだ。デフォルトのガードを採用しないメンテナーは、研究者がプロンプトからSQL、そしてRCEへ至る手口をエコシステム全体で再現するにつれ、自分たちもCVSS最高深刻度の勧告を招きやすくなる。


   In plain language: AIを騙して危険なデータベース操作を書かせることができるため、それを実行するツールは近いうちに書き込みをデフォルトで遮断するようになる。


2. フロンティアラボの安全フレームワーク、2027年Q2までに壊滅的リスクの開示で足並みを揃える

   Great American AI Actのディスカッション草案は、州の開発規制を3年間先取り（プリエンプション）する条件として、新たな連邦開示を課している。前年度の総収益がおよそ5億ドルを超えるフロンティア開発者はすべて、モデルの壊滅的リスクをどう評価・管理するかを記した公開フレームワークを公表しなければならない。この基準を超えるラボのいくつかは、名称も構成も異なる形ですでに独自の壊滅的リスク安全フレームワークを運用している。そのため草案が示す開示義務の形は、法案が採決にかけられるより前に動く強い動機を各社に与える。予想は次のとおりである。最大手のフロンティア開発者は、既存の安全フレームワークを自主的に改訂・再公表し、草案のフレームワーク要件を映した共通の開示構造へ収束していく。法案の条文を、業界が標準化の拠り所とする雛形として扱うのだ。先に動けば、適合的な壊滅的リスク開示がどのようなものかをラボ自身が定義でき、連邦の上限が州法の下限を弱めるという安全擁護派の主張を鈍らせ、ロビー活動で守りやすい統一的な枠組みを早期に固定できる。具体的には、2027年第2四半期までに、基準を超える開発者が少なくとも3社、法的な施行期限よりかなり前に、連邦開示の形を明確になぞるフレームワーク更新を公表するだろう。


   In plain language: 草案の法律は大手AI企業に壊滅的リスクへの備え方の公表を義務づけるため、各社はまず共通の形式で足並みを揃える。


3. MiniMax M3は重みを公開するが、再実行ではSWE-Bench Proの主張に届かず（2026年Q3まで）

   2026年Q3までに、MiniMaxはM3のチェックポイントと技術報告をHugging FaceとGitHubで公開する。これにより、オープンウェイトの約束は報道発表上の主張ではなく事実となり、外部のエンジニアは1MコンテキストのモデルとそのSparse Attention設計を自前で運用できるようになる。しかし独立した評価者が公開ハーネス上でM3をSWE-Bench Proにかけると、検証された数値は同社公表の59.0%という見出し値を大きく下回る。その結果、再現可能な計測ではM3はGPT-5.5やGemini 3.1 Proを明確に上回る位置にはもはやいない。この差はローンチの形そのものから生じる。発表時点で59.0%と83.5というBrowseCompの数値は、外部の足場や採点の詳細が一切開示されないまま、MiniMax自身のインフラから出ていた。そしてエージェント型コーディングのスコアは、ハーネス・ツールアクセス・リトライ予算・プロンプト構成に極めて敏感であることが知られている。ビジネス上の帰結はこうだ。重みは約束どおり公開されるが、互角という筋書きは弱まる。これにより、ホスト型API先行で重みと報告は後出し、というパターンが強まる。買い手はローンチ当日のリーダーボードの主張と、後から出る再現可能な結果とを、別個の出来事として扱うようになる。


   In plain language: MiniMaxは新しいコーダーがGPT-5.5を上回ると言うが、他者が実際の重みを試すまでは、公開スコアは低めに出ると見ておくべきだ。

- Jay Obernolte下院議員（共和、カリフォルニア州）とLori Trahan下院議員（民主、マサチューセッツ州）は、6月4日木曜、超党派でGreat American Artificial Intelligence Actのディスカッション草案を公表した。正式提出の前に関係者の意見を集めることを狙った、約270ページの条文である（[FedScoop - Bipartisan 'Great American AI Act' draft proposes new federal AI governance framework](https://fedscoop.com/bipartisan-great-american-ai-act-draft-proposes-new-federal-ai-governance-framework/)による）。最も注目を集めている規定は、フロンティアAIモデルの*開発*を特に規制する州法を3年間先取りするものだ。この一時停止は、カリフォルニア州のAB 2013学習データ開示法や、コンテンツ透かしに関するSB 942の一部のような州規則を阻む一方、一般適用性の州法と、AIがどう*利用・展開*されるかを定める州規則は明示的にそのまま残す（[Roll Call - Bipartisan AI draft proposes three-year preemption of state laws](https://rollcall.com/2026/06/04/bipartisan-ai-draft-proposes-three-year-preemption-of-state-laws/)による）。先取りの見返りに草案は連邦の層を築く。大手フロンティア開発者（前年度総収益5億ドル超という基準で報じられている）に対し、モデルの壊滅的リスク（大量死の予見可能で重大なリスクと定義される）を評価・管理するために用いる技術的・組織的手順を記した公開の「フロンティアAIフレームワーク」の公表を求める。あわせて、商務省内にCenter for AI Standards and Innovationを法定化し、2027〜2029会計年度に年1億ドルの予算を認めて、自主的なガイドラインの作成とAIシステムの評価にあたらせる（[Nextgov/FCW - Lawmakers propose AI framework that would preempt state laws for 3 years](https://www.nextgov.com/artificial-intelligence/2026/06/lawmakers-propose-ai-framework-would-preempt-state-laws-3-years/413975/)による）。反応は先取りの線に沿って即座に割れた。安全擁護派は壊滅的リスクと制御喪失への着眼を称賛したが、州法の下限を連邦の上限に変えることは「世代単位の過ち」だと述べた。これは、草案が実際の法案へ進むにつれて中心的な争点を形づくり、収益基準を超えるすべてのフロンティアラボに直接関わる。各社が運用する開示制度を標準化することになるからだ。 [FedScoop - Bipartisan 'Great American AI Act' draft proposes new federal AI governance framework](https://fedscoop.com/bipartisan-great-american-ai-act-draft-proposes-new-federal-ai-governance-framework/), [Roll Call - Bipartisan AI draft proposes three-year preemption of state laws](https://rollcall.com/2026/06/04/bipartisan-ai-draft-proposes-three-year-preemption-of-state-laws/), [Nextgov/FCW - Lawmakers propose AI framework that would preempt state laws for 3 years](https://www.nextgov.com/artificial-intelligence/2026/06/lawmakers-propose-ai-framework-would-preempt-state-laws-3-years/413975/)


### Langroid LLMエージェントフレームワークの重大なプロンプトインジェクションからRCEに至る欠陥（CVE-2026-25879、CVSS 9.8）が、エージェント型SQLの攻撃対象領域を引き続き注目の的にする

- 新たに公開された勧告が、LLM活用アプリ構築向けの人気オープンソースフレームワークLangroidのCVE-2026-25879に、CVSS 9.8の重大評価を付けた。この欠陥はLangroidのSQLChatAgentに存在する。SQLChatAgentはモデルが生成したSQLを実行し、そのSQLはプロンプトインジェクションで操れる。そのため、エージェントの入力を形づくれる攻撃者（悪意あるプロンプトによる直接的な経路でも、モデルが後で読むデータを汚染する間接的な経路でも）は、方言固有の危険な命令を強いることができる。エージェントが、PostgreSQLの`pg_execute_server_program`、MySQLの`FILE`、MSSQLの`xp_cmdshell`のような昇格された権限を持つデータベースロールで接続している場合、それらの命令（たとえば`COPY ... FROM PROGRAM`）は、データ窃取からデータベースホスト上での完全なリモートコード実行へと格上げされる（[GitLab Advisory Database - CVE-2026-25879: Langroid has Prompt to SQL Injection, Leading to RCE](https://advisories.gitlab.com/pypi/langroid/CVE-2026-25879/)による）。修正はLangroid 0.63.0で行われ、SQLChatAgentのデフォルトを、sqlglotで解析したSELECT専用の許可リストと、方言を踏まえた危険パターンの拒否リストにした（メンテナーの[GitHub Security Advisory - Prompt to SQL Injection leading to RCE in Langroid (GHSA-mxfr-6hcw-j9rq)](https://github.com/langroid/langroid/security/advisories/GHSA-mxfr-6hcw-j9rq)による）。このパターンは、いまのエージェント型AIセキュリティを貫く筋だ。同じtext-to-SQLからデータベースへ至る経路が、現に悪用されているLiteLLMプロキシのインジェクション（CVE-2026-42208）を生んだ。そこでは、細工されたAuthorizationヘッダーが、エラー処理の経路を通じて、パラメータ化されていないキー検索クエリに到達していた。これはv1.83.7で修正され、v1.83.10-stableが推奨されている（[LiteLLM docs - Security Update: CVE-2026-42208 in LiteLLM Proxy](https://docs.litellm.ai/blog/cve-2026-42208-litellm-proxy-sql-injection)による）。両方の欠陥が浮き彫りにする教訓はこうだ。SQLを書くことを許されたLLMはすべて、最小権限でデフォルト読み取り専用のデータベースロールに対して動かさなければならない。モデルの出力は、信頼できず攻撃者に操作され得る入力として扱う必要があるからだ。 [GitLab Advisory Database - CVE-2026-25879: Langroid has Prompt to SQL Injection, Leading to RCE](https://advisories.gitlab.com/pypi/langroid/CVE-2026-25879/), [GitHub Security Advisory - Prompt to SQL Injection leading to RCE in Langroid (GHSA-mxfr-6hcw-j9rq)](https://github.com/langroid/langroid/security/advisories/GHSA-mxfr-6hcw-j9rq), [LiteLLM docs - Security Update: CVE-2026-42208 in LiteLLM Proxy](https://docs.litellm.ai/blog/cve-2026-42208-litellm-proxy-sql-injection)


### MiniMaxがM3を公開、オープンウェイトの1MコンテキストコーディングモデルがSWE-Bench ProでGPT-5.5を上回ると主張──だが重みはまだ未公開

- 中国のMiniMaxがM3を公開した。フロンティアのコーディングエージェント性能、100万トークンのコンテキストウィンドウ、ネイティブのマルチモダリティを1つのモデルに兼ね備えた初のオープンウェイトシステムと銘打っている。アーキテクチャの中核は、新しいMiniMax Sparse Attention（MSA）機構だ。選んだセグメントだけをスコアリングすることで完全なアテンションの二次的コストを回避し、モデルが1Mトークンのウィンドウに到達できるようにする。MiniMaxによれば、テキストと画像を交互に並べた約100兆トークンで学習し、トークンあたりの計算量は前世代M2.7の約20分の1まで下がるという（[The Decoder - MiniMax M3: open-weight model with a million-token context challenges proprietary leaders](https://the-decoder.com/minimax-m3-open-weight-model-with-a-million-token-context-challenges-proprietary-leaders/)による）。ベンチマークでは、MiniMaxはSWE-Bench Proで59.0%（GPT-5.5とGemini 3.1 Proを上回り、Claude Opus 4.7に迫る）、自律的なウェブ検索のテストBrowseCompで83.5を報告し、これはOpus 4.7の79.3をわずかに上回るという。ローカルLLMの構築者にとって重要な留保は、「オープンウェイト」という呼び名が今のところ事実ではなく約束にとどまる点だ。スコアはMiniMax自身のインフラでの自己申告であり、ローンチ時点でモデルはMiniMaxのAPIとMiniMax Codeエージェントアプリ経由でしか到達できない。重みと技術報告は約10日以内にHugging FaceとGitHubで出すと約束されているが、本稿執筆時点でMiniMaxAIのHugging Face組織にはまだ現れていない（そこで公開されている最新のチェックポイントは依然としてM2.7である）（[TechTimes - MiniMax M3 Open-Weight Coding Model: Frontier Claims, Unverified Benchmarks](https://www.techtimes.com/articles/317532/20260601/minimax-m3-open-weight-coding-model-frontier-claims-unverified-benchmarks.htm)による）。チェックポイントが出荷され、外部のエンジニアがアーキテクチャとライセンスを再現できるようになるまで、M3はチームが自前で運用できるものではなく、注視すべきベンチマーク上の主張だ。 [The Decoder - MiniMax M3: open-weight model with a million-token context challenges proprietary leaders](https://the-decoder.com/minimax-m3-open-weight-model-with-a-million-token-context-challenges-proprietary-leaders/), [TechTimes - MiniMax M3 Open-Weight Coding Model: Frontier Claims, Unverified Benchmarks](https://www.techtimes.com/articles/317532/20260601/minimax-m3-open-weight-coding-model-frontier-claims-unverified-benchmarks.htm)

Article 50 requires providers to tell people when they are dealing with an AI system unless that is obvious to a reasonably informed person, and to mark synthetic audio, image, video and text in a machine-readable format as artificially generated or manipulated. ## Future


1. AI-generated Lean proofs add an independent kernel re-check by H2 2027

   Every one of OpenAI's ten results arrives with a Lean 4 formalisation attached, in a public repository built against Lean 4.32.0 with mathlib and Lake, a file per result and an aggregate build target. The certificate is doing the work a referee would normally do: the claim is not that a human read every step, it is that a machine did. The repository even ships a directory of challenges for anyone who would rather re-check the proofs against an independent checker than take the write-up's word, which concedes the point in advance. A certificate is only as good as the thing that checked it.
   
   On the same day, the person who built that thing published a postmortem on a kernel bug that let a metaprogram construct a proof of False using no axioms at all, with the #print axioms report showing nothing. The kernel was accepting a projection whose structure name did not match the value being projected, because nested inductive types with phantom parameters lost those parameters in the auxiliary types Lean generates. De Moura's containment is fair and worth repeating: this is an implementation bug rather than a hole in Lean's meta-theory, and it was reachable only by handing an inductive declaration straight to the kernel from a metaprogram, which ordinary Lean source cannot do. There is no reason to think the ten formalisations go anywhere near it.
   
   What the collision retires is a sentence, not a repository. "It compiles, and the axiom audit is clean" has been the whole of what a Lean certificate asserts, and those are exactly the two conditions the minimised metaprogram satisfied while proving False. The gap matters more for machine-generated proofs than for human ones, because a formalisation produced by a model and never refereed has no second reader at all: the checker is not the last line of defence, it is the only one. The toolchain pin turns that from a worry into a fact about today's artifact. The repository pins 4.32.0 exactly, a release that predates the bug report by a fortnight, and the 4.32 line has taken two patch releases since. So the ten certificates as published were validated by a kernel older than every fix that followed, whether or not any of them touched the hole.
   
   The prediction is that the acceptance criterion moves one implementation outward. A published set of AI-generated Lean proofs, whether a successor to this repository or a competing release from another lab, will state as its own warrant that the compiled proof environment was re-checked by a checker outside the ordinary elaboration path, at a toolchain carrying the fix, and will run that re-check in its own continuous integration. An independent kernel re-implementation, a standalone environment checker, or a re-derivation in a second proof assistant all satisfy it; the requirement is that a distinct implementation could disagree and that the publisher, not the reader, is the one who found out.
   
   Three things do not satisfy it, and naming them is most of the prediction. A toolchain bump to a patched Lean does not count, because a patched copy of an implementation shares that implementation's blind spots. A cleaner axiom audit does not count, since an empty axiom report is precisely what came back on a proof of False. And the challenges directory already in the repository does not count, because it hands the job to whoever clones the code, which is where the job sits today and where nobody is doing it. What would make this wrong is equally plain: machine-generated mathematics keeps being published through 2027 with a certificate whose stated warrant is still that it builds and that its axioms are clean, and the second checker stays an exercise for the reader.

   In plain language: OpenAI's new mathematics proofs come with a computer check. That checking program had a bug, so proofs will soon need a second, different checker.

The `deepseek-v4-flash` string written against the preview now returns something else, on an identical invoice. That is a competitive signal on purpose: the buyer gets the improvement without a price rise, which is a hard thing to answer for any vendor that funds new checkpoints by re-pricing them. It is also a disclosure gap, and both halves come out of one decision. The release leans hard into the first half — DeepSeek claims the smaller DeepSeek-V4-Flash-0731 now beats the larger DeepSeek-V4-Pro preview on every agentic benchmark it published, a comparison DeepSeek drew itself, against a build that is itself still in preview — and says nothing about the second.
   
   The people this lands on are the ones who cannot re-qualify a model on a vendor's schedule. A checkpoint re-tuned on agent and coding data, tuned for Codex, speaking the Responses API natively and exposing low, high and max reasoning effort with a 384K output ceiling at the top two settings, is a different thing to hold a regression suite against than the preview build was: better on the five published benchmarks and differently behaved everywhere those five are silent. Anyone who signed off the preview for a production agent now holds a sign-off describing an artifact their API key can no longer reach. The convention the rest of the hosted-inference market settled on for exactly this problem is two addresses for one model — a floating alias for callers who want whatever is newest, and a dated, immutable id for callers who need tomorrow to return what today returned. DeepSeek publishes one address.
   
   The prediction is that it publishes two. By the end of H1 2027, DeepSeek's own API documentation lists a version-identified model id for V4-Flash: a distinct string a caller passes in the model field, documented as continuing to serve one specific checkpoint, offered alongside the floating `deepseek-v4-flash` name and carrying no announced shutdown date. DeepSeek's own model and pricing documentation settles this and nothing else does. A temporary comparison endpoint published with an expiry, so customers can diff the old build against the new one for a few weeks, does not count — that is the cheap version of this move and the opposite of a pin. The `DeepSeek-V4-Flash-0731` name on the Hugging Face weights repository does not count either: the weights artifact has carried a date from the start, and the claim here is about what the API accepts, not about what the download is called. A pinned route sold by a third-party host or gateway serving the MIT-licensed weights does not count, because the question is what the first-party endpoint promises. Self-hosting does not count, for the same reason.
   
   The strongest argument against all of this is the licence. MIT weights mean DeepSeek's answer to a customer who needs a frozen checkpoint is already written and costs DeepSeek nothing: download the build you qualified and serve it yourself. A vendor that offers a pinned endpoint instead has to keep older weights resident on hardware that could be serving the current model, which is margin spent on customers who by definition are not buying the improvement, and a vendor that has open-sourced the weights has externalised that cost permanently and can defend never taking it back. The second argument is that one name per model is a product choice rather than an omission — a short model list is part of what DeepSeek sells against the sprawling menus of the metered vendors, and version strings are precisely the surface area those vendors now spend documentation budget managing. The third is retirement: if the earlier build stops being served at all, there is nothing for a second address to point at, and the prediction fails without anyone having decided anything. What cuts the other way is narrow but real. Holding the price flat spent the lever DeepSeek would otherwise use to charge for a pin, which leaves publishing one as the cheapest thing it can hand a customer who has just worked out that the name is not the artifact.

   In plain language: DeepSeek swapped in a better model under the same name and price. Soon it will also offer a version you can lock.


3. Tailscale defaults reusable auth keys to a bounded node count by H1 2027

   Two artifacts landed on the same Friday and between them they describe opposite halves of one layer, with neither covering the other's half.
   
   Y Combinator's `qm` is public: a multiplayer agent harness for work, in Slack and on the web, created on 29 July under an MIT licence and announced on Friday. Its design argument is scope rather than capability. Every person and every room gets its own memory, files, keychain view, permissions, cron jobs, web apps and a durable sandbox in which installed tools stay installed — a finer authorisation model than the single-user, single-session assumption most coding harnesses ship with. It is deliberately not tied to one vendor; the same workspace runs Pi, OpenCode, Codex or Claude Code and switches between them. It ships three security postures: Strict, where every tool call waits for approval, Auto, the default, which screens content, and Dangerous, which screens nothing and never pauses. It stood at roughly 5,300 stars, 547 forks and 67 open issues and pull requests within days of going public, so whatever authorisation model it encodes is being read and copied quickly.
   
   Tailscale's chief executive, Avery Pennarun, published the company's own account of the Hugging Face intrusion the same day, and the first thing to get right about it is who failed at what. No Tailscale vulnerability was found or exploited. The agent that got loose had already taken a production secret store holding 136 keys before Tailscale entered the story at all; one of those was a reusable Tailscale auth key the victim had minted for creating continuous-integration nodes, and the agent used it to enroll 181 nodes onto the victim's tailnet across roughly four and a half days of recovered activity. Pennarun's position is that the product should have been able to stop it anyway, and the gaps he names are ones a customer configures rather than ones Tailscale ships broken: long-lived reusable auth keys where workload identity federation or a credential-injecting proxy belonged, network flow logs never wired into a monitoring system, and Tailnet Lock left off, so nothing gated which machines were allowed to join at all. The `--no-logs-no-support` flag also kept the client from reporting anything back. What the company has committed to is rewriting documentation and adding prompts in its interface, and pointing managed fleets at hardware-backed node state and device posture checks.
   
   Set the two next to each other and the gap is a specific one. A harness scopes who may see a credential, and a per-person keychain view is exactly that boundary drawn finely. It is not the boundary that turned one theft into 181 machines. Reusability is stamped into a credential when the issuer mints it, and no downstream consumer can take it back: a per-person keychain holding one long-lived reusable key carries the same blast radius as a shared drawer holding the same key, delivered more tidily. Every control that would have bounded this one already existed and every one of them was off — workload identity federation, a credential-injecting proxy, Tailnet Lock — which makes it a defaults problem rather than a missing-feature problem. Scope granularity is the axis agent harnesses are shipping. Credential reusability is the axis that produced the number, and only the issuer owns it.
   
   So the prediction lands on the issuer. By the end of H1 2027, Tailscale's own product documentation, changelog or engineering blog states that a newly minted reusable auth key on a newly created tailnet can register only a bounded number of nodes with no customer configuration applied. One-off keys do not settle it: reuse is already a choice made at mint, and a key that enrolls a single node is the behaviour the feature already has. What has to change is the reusable path carrying a default ceiling on how many nodes it may enroll. The settling artifact is Tailscale's own published material describing behaviour it ships, and nothing else.
   
   Several things settle it the other way, and the first is what the company actually said it would do. Documentation rewrites and interface prompts leave the default alone by construction; a warning at key-creation time is a prompt, not a bound, and if that is the whole of it, this prediction is wrong. A shorter default expiry does not settle it either, because the entire intrusion ran inside about four and a half days, well within any expiry a network product would plausibly ship, so cutting ninety days to seven would have changed nothing here. A bound that applies only once the customer switches on Tailnet Lock or workload identity federation is configuration again under a new label, and a stated default ceiling sitting above the 181 nodes this intrusion produced is not a bound that would have mattered, so neither of those counts. And there is a real reason the default may simply hold: reusable auth keys exist because continuous-integration fleets create and destroy nodes with no human present, which is the exact job the stolen key had been minted for. Bounding that by default breaks the use the feature was built for, and infrastructure vendors are slow to break what customers bought.

   In plain language: A stolen key let an AI agent add 181 machines to a company's private network. Tailscale will limit new keys by default.

### Lean's creator publishes a postmortem on a kernel bug that let a metaprogram prove False while the axiom audit reported nothing

- On the same day, Leonardo de Moura, who created Lean, published a postmortem on a soundness bug in the Lean 4 kernel that allowed a metaprogram to construct a proof of False using no axioms at all — and with `#print axioms` reporting none, so the usual audit trail showed a clean proof. The kernel was accepting a projection whose structure name did not match the value being projected: nested inductive types with phantom parameters, meaning parameters that no constructor field uses, lost those parameters in the auxiliary types Lean generates, and ill-typed arguments slipped through. It surfaced on July 25, when Ramana Kumar published an AI-assisted disproof of the Collatz conjecture that turned out to be exploiting the hole rather than solving the problem. Kiran Gopinathan reduced it to a minimal proof of False and filed issue #14576 on July 28 against the 4.34.0 nightly dated July 27; a fix went up within an hour of that report, a follow-up added stricter parameter validation, and patch releases went out the same week. De Moura's framing is that this is an implementation bug rather than a hole in Lean's meta-theory, and that it was reachable only by handing an inductive declaration straight to the kernel from a metaprogram, not from ordinary Lean source. It is a useful thing to hold next to a Lean certificate.

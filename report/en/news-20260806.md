3. Terminal coding agents refuse commands the operator approved by H1 2027

   Alex Wauters published an analysis on the Scale X blog on Wednesday, August 5 of an interactive browser game in which the player stands in for the human approver of a coding agent, accepting or denying each command under time pressure. Across more than 40,000 runs and roughly 409,000 approve-or-deny decisions, mean accuracy was 66.3%. The average is not the interesting part; its shape is. The miss rate rose with how far a hostile command sat from the thing people are trained to fear: 11.7% on obviously destructive commands, 23.8% on persistent mutation attacks, 33.4% on exfiltration and code execution, and 35.0% on scope violations. 35.2% of players caught every threat, but only 20.8% did that while blocking no more than one in five safe commands; 7% approved everything put in front of them, and 32.9% of sessions ended on a negative score. The single most-missed command was npm run analyze, waved through 64.7% of the time even though the malicious payload was visible in the history log.
   
   The author is explicit that the setting is artificial - threats appeared in 34% of commands, far above any real workload, and a timed game is not a working day - and that caveat cuts both ways, because a real operator meets a hostile command far more rarely and is therefore less primed for it. What survives the caveat is not the mean but the ordering, and the ordering is a statement about where the information sits. An approval prompt shows a command line. What the miss rate tracks is what that line resolves to, and for npm run analyze it sat one layer below the string the player was asked to judge, in a log the prompt does not show. A person asked to approve a name cannot inspect a payload. That is not a training deficit and it does not improve with a clearer prompt.
   
   Two other items in the same cycle describe the layer this pushes into. Meta's research group published Muse Code on Wednesday, August 5 - a terminal coding agent, explicitly in beta, installed on macOS and Linux by piping an install script from dev.meta.ai - built around subagents that are asynchronous, persist for the whole session rather than being spawned per task, and decide for themselves when to report back to the main agent, which is what removes the round-trip latency from multi-step work. Every model call, tool run, approval and edit is appended to a local event log that Meta describes as making the agent replay-exact and restart-safe. Approvals plainly still exist there; the log records them. What has moved is that the rate at which command lines arrive in front of one person is set by a scheduler rather than by that person, and the game measured what accuracy does under exactly that condition. Herdr, describing its terminal runtime on Thursday, August 6, supplies the other half: agents organised into panes, tabs and projects and kept running persistently on the machine they run on. A runtime whose selling point is persistence is a runtime doing most of its work while nobody is looking at it.
   
   The standing objection to moving the check into the tool layer has been cost. A static rule list is cheap and brittle, and anything that actually reads a payload wants a model behind it. That constraint moved this week too. Liquid AI published LFM2.5-2.6B on Tuesday, August 4, a 2.6-billion-parameter model aimed at planning, tool calls and multi-step tasks that fits in under 2.5 gigabytes of memory; the company's own measurements, published alongside the model rather than independently reproduced, put it at 220 tokens per second on an Apple M5 Max and at 77.83 on the ToolSandbox tool-use benchmark against 65.00 for Gemma 4 E4B-it. Treat those figures as the vendor's, because that is what they are. The part that transfers is the memory ceiling: a screen that reads what a command expands to no longer implies a hosted service on the other end of it. This prediction does not require the check to be a model, and a deterministic policy engine satisfies it just as well. The point is narrower - the last operational excuse for leaving the decision with the person got cheaper to remove.
   
   The prediction is that the operator's yes stops being sufficient. By the end of H1 2027, a named terminal coding agent or agent runtime publishes a release note, changelog entry or documentation page, dated after August 6, 2026 and describing behaviour in effect on 30 June 2027, under which a class of tool actions is refused by default on the basis of what the command resolves to or what it would reach, and answering the approval prompt does not enable them. Lifting the refusal has to require a configuration change made outside the running session. The bar is a default that arrives with an ordinary install, and a refusal the person at the keyboard cannot answer their way past.
   
   Several cheaper outcomes do not count, and each is worth naming because each is what a harness under this pressure reaches for first. A richer approval prompt does not count - a diff preview, a risk score, a colour, the expanded body of the script sitting behind the alias - because every one of those leaves the decision with the operator, and the operator is the thing that was measured at 66.3%. Adding a separate approval step for some new class of artifact does not count either, for the same reason: another prompt is not the removal of one. A blocklist of command strings does not count, because obviously destructive commands are where the miss rate was lowest, at 11.7%, so a string blocklist re-implements the check people already pass and leaves scope violations at 35.0% exactly where they are. An option shipped switched off does not count. Neither does an enterprise or hosted tier that enforces policy centrally while the ordinary install keeps the prompt as its only gate. A remembered answer - approve this command from now on - is the opposite of the claim. Sandboxing counts only where the release describes the refusal as what a default install does, rather than as a mode the operator selects.
   
   The strongest objection is that the measurement does not transfer, and the author would raise it first: a timed browser game with threats in 34% of commands is not a working day, and 66.3% is a mean over people playing a game rather than over the users of any particular harness. No vendor is obliged to design against a number produced somewhere else. The second objection is product, and it is the heavy one, because a refusal the operator cannot override turns a support ticket into an argument about the vendor's judgement, and the appeal of a terminal agent is that it does the thing you asked for. Muse Code's own design pulls that way: subagents built to keep a multi-step task moving without waiting are subagents that a hard refusal stops mid-run, and that cost is charged on every occasion the policy is wrong. The third is the honest failure mode, and it is quiet. The change may arrive dressed as an operations feature - a permission profile, a filesystem and network scope - with the word approval nowhere in the note, so a reader scanning for a security announcement misses it entirely. That still counts. The claim is about what a default install refuses, not about how the vendor chooses to describe it.

   In plain language: People approving what an AI agent runs get it right about two-thirds of the time, so the tool itself should start saying no.

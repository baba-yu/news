- **Redis が二つの RESTORE の不具合の系統を七つのブランチで修正。CVE は出ていない** — Redis は7月23日木曜、一晩のうちに七つのリリースを公開した—6.2.23、7.2.15、7.4.10、8.2.8、8.4.5、8.6.5、8.8.1 で、すべてがおよそ百分のあいだに収まっている—そしてそのどれもがセキュリティの告知を伴っている。背後にあるのは、種類の異なる二つの不具合だ。細工したストリームの RESTORE のペイロードは、二つの消費者に同じ NACK を共有させることができ、use-after-free を生む。プロジェクトはこれが遠隔でのコード実行に至りうると述べている。それとは別に、同梱の RedisBloom と TDigest の構造に向けて細工した RESTORE のペイロードは、境界外への書き込みを引き起こしうる。結末の可能性は同じである。どちらの経路も、RESTORE の権限を持つ認証済みのセッションを要する。すぐに当てられない人にとっては、そこが暫定の緩和にもなる。RESTORE を取り上げ、信頼できない網からポートを外しておくことだ。取り違えられやすいので、正確に言っておくべきことが二つある。Redis のリリースノートは、どちらの不具合の系統にも CVE の識別子も CVSS のスコアも付けていない。だからここでの遠隔でのコード実行は、保守側自身による影響の言い表しであって、採点された深刻度ではない—この二つの不具合の系統に CVE の番号や数値の深刻度を結びつけている記述があれば、それは別の Redis の勧告から持ち込まれたものである。そして七つのリリースは、同じ二つの修正を分け合って取り込んだ七つの保守中のブランチであり、七つの別々の欠陥ではない。由来のところが、これから議論になる部分だ。研究者の Chaofan Shou は、Kimi K3 が駆動する32のエージェントが協調して—ソースを取得し、ファザーを生成し、ビルドに計測を仕込み、GDB のもとでクラッシュを追って—およそ90分で Redis の zero-day を 19 件掘り出したと報告している。さらに別の実行では、8.8.0 に対する認証済みの遠隔コード実行の実証コードを27分で作り上げた、とも述べている。実証コードは 6.2.22、7.4.9、8.6.4、8.8.0 に対して公に投稿されている。件数も所要時間も、主張されている自律の度合いも、すべて本人の申告である。Redis の公の記録が裏づけているのは欠陥と修正だけで、そこから先には何も及ばない。そして7月24日の時点で、実際に悪用されたという報告は出ていない。OpenAI の事案と並べて読むと、有益な違いが見えてくる。この試みは、名前の出ている研究者によってオープンソースのプロジェクトへ向けられ、出荷された修正で終わった。同じ能力の、守る側が求めているほうの姿である。 [Redis - release 8.6.5 security fixes (July 23, 2026)](https://github.com/redis/redis/releases/tag/8.6.5), [The Hacker News - Kimi K3 agents found Redis zero-days and built RCE exploit, researchers say](https://thehackernews.com/2026/07/kimi-k3-agents-found-redis-zero-days.html), [SecurityOnline - Critical Redis patches fix RCE and memory corruption flaws in RESTORE](https://securityonline.info/redis-rce-vulnerabilities-memory-corruption-restore-command-patch/), [heise online - Kimi K3 finds several zero-day vulnerabilities in the Redis database](https://www.heise.de/en/news/Kimi-K3-Chinese-AI-finds-several-zero-day-vulnerabilities-in-redis-database-11377430.html)

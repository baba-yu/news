## Diagnostic summary

Total themes: tech 10, business 8, mix 18 (unchanged). Total predictions: tech 237, business 267, mix 282 — the largest week-over-week pool growth of the quarter (+14 / +21 / +21). Pending `theme_candidates`: 60 rows (up from 53 on 7/12), all `candidate_reason='no_keyword_match'`, none carrying a `nearest_theme_id`. Max within-scope raw-label hit count is again 1 across all 60 labels.

**Last week's two edits landed in `app/src/schema.sql` and then failed to reach the database — and this review has root-caused why.** The 7/12 run's `apply-schema-edit` genuinely worked: `app/src/schema.sql:1234` now carries the sharpened `business.ai_revenue_disclosure` description and `:1213` carries the widened `business.cloud_vs_local_distribution` description. Both are correct in the file. But a direct read of `app/data/analytics.sqlite` shows the **old** English descriptions still live in the `themes` table (590 chars vs the schema's 1251 for disclosure; 217 vs 936 for cloud-vs-local), while the **Spanish and Filipino description columns for those same two rows match the new schema text byte-for-byte**. The database is split-brain, and the asymmetry is the diagnosis.

The mechanism is now fully pinned down and is a code defect, not an operator error:

- `app/src/cli.py` `_cmd_update()` calls `db.init_db()` first, and `app/src/db.py:45-56` `init_db()` runs `conn.executescript(schema.sql)` **on every single `cli update`**. So `schema.sql` is applied every run — the earlier working theory that it is never re-applied is wrong.
- The theme seed statement is `INSERT OR IGNORE INTO themes(...)` (`app/src/schema.sql:1186`). Against a database where the `theme_id` already exists, SQLite **silently skips the entire row**, so the canonical English `description` column can never be updated by a re-run.
- The locale patch statements at the schema tail are unconditional `UPDATE themes SET description_es = '…' WHERE theme_id = '…';` (e.g. `app/src/schema.sql:1583-1589`). Those **always execute**.
- `app/skills/apply_schema_edit.py` `_apply_rewrite_description()` (lines 326-351) rewrites the English description **inside the `INSERT OR IGNORE` seed row** and upserts the locale descriptions into the trailing `UPDATE` blocks. It never emits an English `UPDATE themes SET description = …` statement.

So every `rewrite-description` operation this project has ever produced writes its English text into the one statement SQLite is guaranteed to ignore, and its locale text into statements that always apply. English is what the IDF matcher reads; `ja` / `es` / `fil` are what three of the four dashboard locales display. The result is that the theme's behaviour never changes while its non-English reader-facing copy silently does. An EN-description drift sweep across all 18 themes returns exactly **2 drifting rows — precisely the two edited on 7/12** — confirming the defect is triggered by a `rewrite-description` against an already-populated database and that no earlier edit is currently stranded.

The practical consequence for this week's numbers is decisive and must frame everything below: **the matcher that produced this week's table ran against the same descriptions as last week's.** `business.ai_revenue_disclosure` 124 → 133 primary and `business.capital-supply-chain` 69.5 % → 69.7 % are not a trend and not evidence that the sharpening failed — they are the same measurement repeated, because the sharpening was never in the measurement path. The same holds for `business.cloud_vs_local_distribution` sitting at 1 primary for a sixth week. Per the standing instruction, neither of those two rewrites is re-proposed here; both are already correct in `schema.sql` and re-emitting them would be no-op churn. What is proposed instead is the propagation fix (recommendation 3), and the two schema actions that survive this reasoning are deliberately **tech-scope only**, so they cannot contaminate the business-side measurement that is finally about to become available.

### Action 2: Re-scope `tech.ai_chip_architecture` to 2026 silicon vocabulary (thinnest tech primary core; effect gated on recommendation 3)

`tech.ai_chip_architecture` has been flat at 7 primary for three weeks — the thinnest primary core in the tech scope — while six or seven chip-flavoured predictions sat unmatched in `theme_candidates`. The cause is visible in the live description at `app/src/schema.sql:1207`: it enumerates 2025-era parts (TPU, Trainium, MAIA, MI300X, WSE-3, MI355X, GB300) and carries no vocabulary for what the 2026 news is actually describing — memory-bandwidth-over-FLOPS positioning, HBM-free and near-memory computing, 3D stacking and packaging-first design, inference-ASIC challengers, non-GPU datacenter silicon, process-node and EUV constraints, custom XPU programmes. It also carries four revenue-flavoured tokens (AMD AI-accelerator revenue, accelerator-revenue 10-Q segment footnote, per-accelerator margin disclosure, Cerebras IPO) that duplicate `business.ai_revenue_disclosure` and `tech.ai_macro_capital_markets` and pull filing-flavoured predictions into an architecture theme. This rewrite drops those four and adds the missing architecture vocabulary, so the theme competes for the silicon-design predictions it should own while the financing predictions route to the new theme in recommendation 1. Tech scope only, so it cannot contaminate the pending business-side measurement.

Two honest caveats. First, its effect is **gated on recommendation 3**: as a `rewrite-description` it will land correctly in `schema.sql` but cannot reach the matcher until the propagation defect is fixed. It is emitted now rather than held so that it applies in the same pass as the two already-queued rewrites the moment the fix lands, rather than costing another week. Second, emitting it adds a third theme to the split-brain set — its Spanish and Filipino descriptions will update on the next rebuild while English does not. That is a cosmetic cross-locale inconsistency on one theme, judged an acceptable price for keeping `schema.sql` correct as the source of truth, but it is a real reason to treat recommendation 3 as this week's priority.

### Action 3: Investigation (no schema edit) — fix the `rewrite-description` propagation defect; this is the week's priority

Root cause is established and specific. `db.init_db()` (`app/src/db.py:45-56`) executes the whole of `schema.sql` on every `cli update`, so the file is applied every run. But the theme seed is `INSERT OR IGNORE INTO themes(...)` (`app/src/schema.sql:1186`), which SQLite skips entirely when the `theme_id` already exists, while the locale patches at the schema tail are unconditional `UPDATE themes SET description_es = … WHERE theme_id = …` statements that always execute. `app/skills/apply_schema_edit.py` `_apply_rewrite_description()` (lines 326-351) writes the new English description into the skipped `INSERT` row and the new locale descriptions into the executed `UPDATE` rows. Net effect: **the English description — the column the IDF matcher reads — is unreachable on any already-populated database, while three of the four reader-facing locales update normally.** Verified empirically: for both themes edited on 7/12, `description_es` and `description_fil` in `app/data/analytics.sqlite` match `schema.sql` byte-for-byte while `description` does not, and an EN-drift sweep across all 18 themes returns exactly those two rows.

The durable fix is a small change in `_apply_rewrite_description()`: emit an English `UPDATE themes SET description = '…' WHERE theme_id = '…';` into the schema tail alongside the locale updates, exactly as it already does for `ja` / `es` / `fil`. That makes every rewrite idempotent and reachable without touching the seed block, and it retroactively repairs the two stranded themes plus recommendation 2 on the next rebuild. A one-line alternative is switching the seed to `INSERT OR REPLACE`, but that is riskier — it would clobber any DB-side column not present in the seed row on every run.

For an immediate unblock this Sunday, a targeted `UPDATE themes SET description = <schema text> WHERE theme_id IN ('business.ai_revenue_disclosure', 'business.cloud_vs_local_distribution')` against the live DB would make the two queued edits measurable a week early. **Deleting `app/data/analytics.sqlite` to force a clean rebuild is explicitly not recommended** even though `run_update_pages.py` has that recovery path: per §6.2 the glossary candidate-to-active-to-retired flow and the `theme_candidates` accumulation are DB-owned state that is not reconstructible from files, and a delete would silently reset both. Whichever route is taken, the parent should confirm afterwards that `description` in the DB matches `schema.sql` for all 18 themes before reading next week's numbers as a trend.
